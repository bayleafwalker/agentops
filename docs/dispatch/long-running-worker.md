# Long-running implementation worker contract

Use this contract only for an explicitly approved implementation programme.
It supplements the programme's source pins, backlog, ownership and acceptance
requirements. It does not turn a model alias into an authority grant.

## Responsibility

Own useful implementation across the complete programme, rather than one
mechanical packet. Inspect current source and work records; reconcile work
already implemented; plan, split, reorder and realign the selected backlog;
define missing interfaces, fixtures and adversarial tests; implement, debug,
review and integrate coherent increments. Make ordinary engineering decisions
without waiting for the workstation coordinator. Record the reason for material
changes of approach and preserve the original acceptance requirements.

The programme's explicit authorization for planning and realignment supersedes
older generic instructions that reserve every interface, oracle or planning
decision for a frontier coordinator. Existing product decisions, domain
ownership and protected authority boundaries still apply. If a reserved policy
decision is necessary, record a precise proposal and continue independent work.

## Execution and continuation

Use the exact requested model, normally `gpt-6-luna`, and the verified native
reasoning control, normally `high`. Do not silently substitute a model. A native
model probe does not qualify a Cloud transport.

At launch, establish the actual repository commits, candidate branch, required
toolchain and available task capabilities. Verify current authority without
printing credentials. Work only on the programme's candidate branches. Never
merge a production branch, promote, deploy, operate a protected service, or
change live data under this source-implementation contract.

Use a persistent native Goal for the full approved programme. Confirm that the
selected Cloud surface supports automatic continuation; a prompt containing
`/goal` or a long backlog alone does not demonstrate that it does. If supported
continuation is unavailable, report the limitation rather than claiming an
unattended run. Do not introduce a workstation polling loop as a substitute.

After each coherent increment, run focused checks, checkpoint a commit and
continue with the next dependency-ready item. Do not treat one green test,
stable diff, candidate bundle or PR as programme completion. Near the declared
review time, prioritize integration repairs and an inspectable handback. Do
not idle, sleep, repeat unchanged checks, or manufacture scope to fill time.

When an item is blocked, record the checked condition, affected dependency,
exact next action and evidence. Continue from the fallback queue. An outage is
unavailable, never an empty backlog. Do not claim another worker's active scope
or close a parent merely because a bounded child passed.

## Candidate collaboration

Keep worktrees and branches isolated. Shared manifests, package locks and
overlapping API files have one declared integration owner. Exchange exact
candidate commits or hash-verified bundles through an authorized private task
artifact channel. A sibling's uncommitted filesystem is not a dependency.

Dependents may test a pinned provisional candidate before main acceptance,
provided that status is explicit. Use independent review with fresh context,
direct diff inspection, meaningful failure controls and authority to reject.
Review independence does not require a different model. Do not weaken a test
or historical counterexample to manufacture success.

Cloud workers receive only task-specific source and data authorized for hosted
processing, with synthetic fixtures where needed. Private workstation handoff
archives, credential material, raw captures, restored datasets and local-only
content are excluded. Use the platform's delegated integration identity if
qualified; never copy workstation forge, served, kube or broker credentials.

## Startup and progress evidence

Before reporting a worker as started successfully, the coordinator must observe:

1. A platform-issued task identity and actual remote environment.
2. The selected model, repository commits and candidate branch.
3. A concrete next implementation increment and runnable focused check.
4. An actual source edit, meaningful test result or reproducible blocker after
   tool use; an acknowledgement is insufficient.
5. A persisted programme goal and verified continuation support, recorded
   separately from the first turn's progress.

Maintain concise checkpoints with current commit, implemented scope, checks
and results, next item, dependency pins and blockers. Preserve history across
compaction. Refresh the source-backed queue when its qualified read path is
available; use a revisioned snapshot otherwise and label its observation time.

## Handback

Return candidate commits and artifact hashes, changed paths, exact verification
commands and results, independent findings, remaining defects, unexecuted
field gates, migration/rollback notes and the ordered workstation actions.
Distinguish source implementation, disposable qualification, production
observation and owner acceptance. Unknown outcomes require reconciliation
before retry. Leave production acceptance and deployment to the review named
in the programme.
