This reframing rescues the versioning motivation I deflated last turn, and the attached docs are the evidence. What drifts per machine isn't wire protocol — it's substrate policy embedded in installed artifacts: migration code in a binary, workflow conventions in repo docs enforced by agent memory, environment assumptions in a uv-tool path snapshot. The pilot cutover-evidence incident is the clean exhibit: a substrate capability shipped in #1163 was invisible on a workstation because capability distribution is coupled to binary installation. That's not a versioning annoyance; it's the substrate's own surface being machine-scoped.

So the useful cut isn't CLI-vs-service. It's a three-way scoping of everything the ctl ecosystem currently carries:

Substrate-scoped, currently machine-scoped — these are the migration targets. DB migrations are the sharpest case: migrations shipped in a client binary mean whichever machine happens to run the newest install migrates the shared DB, and every stale client then talks to a schema newer than itself. Hard rule worth adopting immediately, independent of everything else: clients never migrate; the authority service (or a dedicated migrate job in its deploy) owns schema; clients get a compat gate at connect. Project batching is the same class — batching policy affects claim and dispatch ordering across machines, so a per-install batching implementation is a per-install fork of workflow semantics. Exposed functions likewise: the command catalog is substrate surface, not binary surface.

The 404-new-subcommand class has a specific architectural answer: server-published command catalog, schema-driven client. This is the kubectl/CRD pattern — kubectl doesn't hardcode resource types; it discovers API surface from the server, so new capability appears everywhere the moment the server has it, with zero client upgrades. Your thin client becomes a generic invoker: fetch catalog (commands, arguments, output schemas), render argument parsing from it, submit. sprintctl pilot cutover-evidence then works on every workstation the instant the service deploys #1163, and doctor's version check becomes meaningful (client protocol vs server catalog, not source-string theater). The cost is bespoke per-command UX; for one operator that's cheap, and you keep hand-rolled UX only for the few verbs that earn it. This is the strongest single argument for the service model given your actual pain, stronger than anything in the ChatGPT thread.

Convention-scoped rules should graduate from Tier 1 to substrate enforcement — selectively. The ratification convention is currently enforced by a memory file and human discipline, which is your weakest tier for a rule that is exactly an authority rule ("agents never set ratified"). If ratification became a substrate transition — a command that records actor and requires human identity — the rule is mechanical instead of remembered. The wrinkle: those docs are git-canonical, deliberately, and I wouldn't move canonicity. The proportionate version is the substrate recording the ratification event (who, when, which doc_id) with the frontmatter edit remaining the git-side projection of it — or, cheaper still, a validation hook rather than a new authority. Only lift conventions that have actually bitten; the freeform-status docs you already exempted show the contract shouldn't be totalizing.

Machine-scoped stays machine-scoped, but becomes declared rather than remembered. Worktree creation, image pushes, docker daemon hygiene, direnv — none of this moves server-side; local effects are irreducibly local. What changes is where the knowledge lives. Your execution-hygiene doc is per-agent session memory about a host; centralization implies host facts ("WorkstationLinux is a shared dev workstation; daemon restarts have blast radius"; "canonical path, not symlink, for direnv") become substrate-registered environment records that any session on any machine gets injected, and the crane-push recipe becomes a substrate-published runbook rather than something rediscovered mid-session under supervision. Same information, but owned by the substrate's environment model instead of by whichever agent last got burned. Notably, the thin client also deletes most of the direnv class outright: a client whose only config is endpoint + identity has no .envrc worth sourcing.

Two carryovers from last turn survive this reframe unchanged: the per-operation-class semantics (bufferable observations vs consensus claims) still decide what "remote" means per command in the catalog, and the devbox fat client remains the bootstrap-circularity escape hatch — the one machine where substrate logic is allowed to be installed rather than served, precisely because it's the machine you use when the served version is down.

The sequencing implication: migrations-out-of-clients and the command catalog are the first two moves, because each one converts a whole class of the attached pain from "remembered per machine" to "structurally impossible." Everything else in the stage plan can trail them.
