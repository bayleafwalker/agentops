# Two-year agentic ecosystem: KAOS goal-to-delivery roadmap

Status: **operator-requested planning scope, 18 October 2026**. This records the request to backcast the assessed two-year goal state into project plan items. Planning and landing are authorized; implementation, deployment, operational qualification and new effect authority are not implied. October 2028 is a design horizon, not a delivery promise. Dependencies and evidence order work, without calendar buckets or invented staffing.

The [October15 product direction](https://github.com/bayleafwalker/vuoro/blob/main/docs/direction/2026-10-15-product-direction.md) and [October17 estate plan](2026-10-17-estate-evolution-plan.md) retain ownership and trust boundaries. Native products own execution, scheduling, sessions and model choice. Vuoro owns portable work, evidence, authority/delegation and learning contracts. This is a requirements trace, **not another writable work ledger**. Served Sprintctl owns activity status; repository plans own requirements. Existing items are reused with explicit scope clarification, not silently closed or replaced.

## Goal state and KAOS method

**G00: Achieve useful durable delegation with capacity growing faster than supervision and maintenance burden.** A person expresses an objective, agents carry it across sessions and machines, protected owners accept exact results, and measured learning improves subsequent work. G00 requires G01 through G12 together (**AND**). Activity counts or a single demonstration do not establish that conjunction.

This is semi-formal KAOS: goals, AND/OR refinement, objects, responsible agents, assumptions, obstacles and operational requirements. Traceability and dependency consistency are checked; no temporal model-checking proof is claimed. A KAOS agent can be a person, deterministic service or supplier product, not just an LLM. Feature engineering means deriving product capabilities/variants from goals, not ML predictor construction.

Method sources: [van Lamsweerde's KAOS research](https://webperso.info.ucl.ac.be/~avl/gore.php) and [van Lamsweerde/Letier obstacle handling](https://research.dial.uclouvain.be/entities/publication/de49727c-3abf-4113-8b8d-8b24334e4f7e). Estate-specific decisions below are this roadmap's design, not claims from those sources.

## Leaf requirements, operations and assumptions

Each Gxx AND-refines into the acceptance predicates of its mapped activities plus applicable safety invariants. Each activity is a bounded requirements package with the delivery decomposition below. Software-owned leaves are requirements; obligations kept by humans/providers are expectations, never asserted to be enforceable by Vuoro.

| Requirement | Goal | Observable operation | Expectation / assumption |
|---|---|---|---|
| R01 | G01 | Explain/amend/stop objective and bounded affected work with history | Domain owner defines value; AO-K02 predeclares thresholds |
| R02 | G02 | Read current owner facts with source, scope, revision, observed-at | Unreachable source returns unavailable, not absent |
| R03 | G03 | Retrieve/correct/supersede exact authorized context; show source impact | Source semantics and human canon remain domain-owned |
| R04 | G04 | Bind attempt/checkpoint/artifact and resume without predecessor chat | Runtime exposes handles or adapter declares unsupported |
| R05 | G05 | Discover qualified arrangements and placement constraints | Harness selects; supplier capability claims require qualification |
| R06 | G06 | Evaluate current delegation and exact operation at protected boundary | Target revocation latency is explicit, not inferred away |
| R07 | G07 | Reconstruct request, artifact, receipt, observation and Decision | Missing provider evidence stays missing |
| R08 | G08 | Account/reserve one commitment budget; report enforcement exposure | Local ledger cannot stop unmediated provider spending |
| R09 | G09 | Reconcile uncertain effect and restore whole application | Owner supplies RPO/RTO and recovery access |
| R10 | G10 | Enforce data/egress rules and qualify dependency changes | Provider data handling requires verified policy/contract evidence |
| R11 | G11 | Compare arrangements on accepted comparable outcomes | Insufficient sample or capture produces inconclusive result |
| R12 | G12 | Onboard, explain exceptions, recover, export and replace supplier | Independent users participate; silence gives no consent |

Representative invariant forms (G = always; F = eventually subject to stated availability):

- G(Apply(effect) -> CurrentGrant(actor,effect,resource) AND ExactArtifact(effect) AND OwnerAccepts(effect)). Proposal is never its own grant.
- G(UnknownEffect(effect) -> NOT BlindRetry(effect)); reconcile target state first.
- G(UseAsAuthority(context) -> CurrentSource(context) AND AuthorizedRead(context)). Confidence does not establish authority.
- G(Accept(work,artifact) -> CurrentWorkRevision(work) AND DigestBoundEvidence(artifact)). Report, receipt, observation and acceptance stay separate.
- G(Continue(work) -> SameDurableWorkIdentity(work) AND FreshAttemptAuthority(work)). Provider session is only a reference.
- G(Compare(cohort) -> VisibleDenominator(cohort) AND VisibleCoverage(cohort)). Inadequate coverage is inconclusive.
- G(Stopped(commitment) -> NOT NewProactiveProposal(commitment)); retain history subject to retention policy.
- G(Admitted(work) AND AvailableDependencies(work) AND AvailableQualifiedRuntime(work) -> F(Result(work) OR ExplicitBlocked(work) OR Cancelled(work))). Outage is not a liveness guarantee.

## Backcast, increments and delivery lifecycle

Backcast from AO-K06: seven end-state demonstrations require field-qualified continuity/results/recovery/learning/swaps/domain outcomes and independent-user operation. Those require the feature increments below, which require current-source reconciliation and owner observations. Source implementation never substitutes for deployment evidence.

1. **Establish evidence and scope:** AO-K01/AO-K02, AS-K01, NX-K01, DC-K01. First-ready discovery; reconcile current state and predeclare measures.
2. **Prove a useful complete workflow:** VU-K02, HLA-K01, SP-K01/SP-K02, CB-K01/VU-K06 and AS-K02. Preserve objective, continuation, protected effect and recovery.
3. **Make context and capacity reusable:** VU-K03..05, LI-K01/02, DC-K02 and BW-K01. Onboard alternatives only within qualified boundaries.
4. **Make learning and attention operational:** AL-K01/02, VU-K08/09, CL-K02/03 and HLA-K02..04. Measure outcomes and attention; change delegation only through existing authority.
5. **Support independent users and supplier changes:** VU-K10 and CL-K01/04/05. Actual swaps, install/upgrade/restore/export, and tenant design before exposure.
6. **Demonstrate sustained domain usefulness:** SC-K01/02, FW-K01, AE-K01, AO-K05/AO-K06. Domain work can progress independently where dependencies allow.

These are dependency increments, not date buckets. Discovery/design can advance while preserving missing runtime facts; qualification/rollout cannot assume them away. Operator review/recovery capacity bounds work in progress; AO-K02 measures that budget. Estimate effort after owner discovery rather than inventing team capacity.

**Each activity has six delivery stages:** (1) reconcile source/live state and existing items; (2) specify requirements, responsibility, sourcing and failure cases; (3) implement the missing capability or configure/onboard the chosen product; (4) qualify success and obstacle cases; (5) release/install/roll out under existing authority and observe behavior; (6) document support/rollback/export and measure useful outcomes. Experiments end with evidence-backed adopt/retain/revise/close decisions. Source, release, deployment, field qualification and acceptance are separate evidence states. Planned scope stays admitted while later stages wait on named conditions.
